Sécurité de vos paiements

edUloc met en œuvre les standards internationaux les plus stricts pour protéger vos transactions.

🔒 Paiements par Carte Bancaire (PCI DSS)

Norme PCI DSS Niveau 1

Nous respectons la norme Payment Card Industry Data Security Standard (PCI DSS) qui impose des exigences strictes pour la protection des données de cartes bancaires.

VISA-01 : Externalisation sécurisée

La saisie des cartes est confiée à un prestataire certifié PCI DSS. edUloc ne manipule jamais directement les numéros de carte complets.

En savoir plus sur PCI DSS →

VISA-02 : Interdiction de stockage du CVV

Le code de sécurité CVV n'est jamais enregistré dans nos systèmes, même de manière chiffrée. Cette interdiction est absolue selon PCI DSS.

Pourquoi le CVV ne peut pas être stocké →

VISA-03 : Authentification 3D Secure

Tous les paiements sont protégés par Visa Secure (EMV 3-D Secure). Votre banque peut vous demander une authentification supplémentaire (code SMS, notification, biométrie).

Comprendre Visa Secure →

VISA-04 : Vérification serveur

Une authentification 3D Secure réussie ne suffit pas. Nous vérifions systématiquement le statut financier de la transaction auprès du prestataire avant de confirmer votre réservation.

📱 Mobile Money (GSMA)

Conformité GSMA Mobile Money API

Nous suivons les spécifications de la GSMA Mobile Money API pour garantir des intégrations sécurisées avec les opérateurs (Orange Money, MVola, Airtel Money).

MM-01 : Protection de votre PIN

edUloc ne vous demandera jamais votre code PIN Mobile Money. La saisie du PIN se fait exclusivement dans le canal officiel de l'opérateur (USSD ou application).

  • Aucun agent edUloc ne peut vous demander votre PIN
  • Aucun PIN n'est enregistré dans nos systèmes ou dans Odoo
  • L'authentification reste dans le dispositif de l'opérateur
Spécifications GSMA →

MM-02 : Distinction des statuts

Une réponse "202 Accepted" signifie que la demande est en traitement, pas que le paiement est réussi. Nous attendons la confirmation finale avant de valider votre réservation.

États internes :

  • PENDING - Paiement en cours
  • SUCCEEDED - Réussite confirmée
  • FAILED - Échec confirmé
  • CANCELLED - Annulation confirmée
  • EXPIRED - Expiration confirmée

MM-03 : Vérification serveur obligatoire

Avant toute confirmation, notre backend vérifie la transaction auprès de l'opérateur en contrôlant :

  • Référence interne et référence opérateur
  • Montant et devise
  • Compte marchand bénéficiaire
  • Statut final
  • Correspondance avec la réservation

Nous utilisons l'API de consultation de statut pour couvrir les cas où le callback ne serait pas reçu.

Documentation API de statut →

MM-04 : Preuves clients non suffisantes

Un SMS de confirmation ou une capture d'écran fournie par le client ne suffit pas à valider automatiquement une réservation. La confirmation doit provenir des interfaces officielles du prestataire.

🛡️ Mesures Techniques Communes

SEC-01 : HTTPS Obligatoire

Tous les échanges sont chiffrés via HTTPS/TLS en production.

SEC-02 : Protection des Clés API

Les secrets API sont stockés uniquement côté serveur dans un gestionnaire de secrets. Jamais dans le frontend ou Git.

SEC-03 : Calcul Serveur des Montants

Le montant à payer est calculé côté serveur à partir de la réservation, sans faire confiance au navigateur.

SEC-04 : Contrôle d'Accès

Vérification systématique des autorisations avant toute opération de paiement.

SEC-05 : Authentification des Notifications

Les webhooks sont vérifiés via signature cryptographique ou certificat.

SEC-06 : Page de Retour Non Fiable

Une page de retour "succès" n'est jamais considérée comme preuve suffisante.

SEC-07 : Idempotence

Les requêtes répétées ne produisent pas plusieurs validations ou remboursements.

SEC-08 : Limitation des Tentatives

Surveillance des comportements anormaux et limitation des tentatives.

SEC-09 : Séparation des Environnements

Environnements test et production strictement séparés avec identifiants différents.

SEC-10 : Journalisation Sécurisée

Logs complets sans jamais enregistrer de codes secrets ou données sensibles.

SEC-11 : Rapprochement Régulier

Réconciliation régulière des transactions internes avec les relevés du prestataire.

Intégration Odoo CRM

Données visibles dans Odoo

  • Référence client et réservation
  • Moyen de paiement et prestataire
  • Montant et devise
  • Référence de transaction
  • Statut du paiement et date de dernière vérification
  • Historique des actions

Restrictions imposées

  • ❌ Un agent ne peut pas transformer manuellement un échec en succès
  • ❌ Les secrets API, PIN et codes d'authentification ne figurent jamais dans le CRM
  • ❌ Le CVV n'est jamais conservé dans Odoo
  • ✅ Les régularisations exceptionnelles nécessitent une procédure distincte avec justificatif
  • ✅ Les remboursements sont réservés aux rôles autorisés
